# Task assignment command — implementation contract

Scope: FR-TASK-002, BR-001/002/003/004/020, SSS §9.1, ADR-0003/0012 and architecture A-02. This increment implements assignment, not acceptance/execution or full workflow runtime.

- `POST /api/v1/tasks/{id}/assign` accepts exactly one `targetType` (`USER` or `DEPARTMENT`), `targetId`, and optional plain-text `note`. Live `tasks.assign` is a tenant action with MANAGER system-role default; every target additionally requires configured management scope. Role names never authorize a request. User targets resolve their current department; an unscoped user cannot be assigned by inventing tenant-wide management scope.
- Only DRAFT/REJECTED may become ASSIGNED. Unpinned Tasks use the exact canonical Domain policy. Pinned workflow/SLA runtime is not yet implemented and must fail closed, never fall back to the unpinned graph. No new state or table is introduced.
- The workflow engine is the sole in-memory state mutator and produces nonpersisted mutation evidence for the persistence guard. Existing detached/forged state updates remain rejected. The Task row is locked; targets are same-tenant and active, and live authority is rechecked after locking.
- A rejected current assignment is ended without changing its original target/decision. A new immutable-origin assignment is inserted. State, assignment, truthful audit and in-app recipient events commit atomically. Department recipients are active members at assignment time; responsibility stays with the department queue until the separately approved claim use case. Email delivery remains a required subsequent operational integration, not removed from scope.
- Optional Idempotency-Key follows TD-03: tenant+actor+TASK.ASSIGN scope, normalized fingerprint including TaskId, conflicting payload 409, original response replay and database serialization/unique index. Current action permission and target management scope are still required on replay. Active-target eligibility gates new execution, not replay of a historical result; replay never reassigns or emits another notification. Return 200 `{taskId,assignmentId,status,assignedAt}`.
- Existing people/department directory contracts can supply target choices; their frontend visibility never replaces assignment authorization. A manager without configured scope receives the existing 403 TASK.TARGET_OUT_OF_SCOPE response.

Required tests: exact default graph; no pinned fallback; actor/tenant/target eligibility and scope; revoked scope; concurrent different keys on one draft produce one assignment; keyed identical/conflicting retries; old rejected history preservation; audit failure rolls back state/assignment/notifications; recipient isolation; detached update rejection; real browser assign → current responsibility and assigned-user visibility. Acceptance/execution, Request-linked assignment and email delivery remain required for full Task acceptance.
